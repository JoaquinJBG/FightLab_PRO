# P0.1 — Banda de carga tipo Strava (diseño)

> Fecha: 2026-07-02 · Estado: borrador, pendiente de revisión del usuario · Tipo: diseño de feature
> Deriva de: [`2026-07-02-vision-ampliada-v2-benchmarking.md`](./2026-07-02-vision-ampliada-v2-benchmarking.md) §3.1

## 1. Problema

La vista de Carga (`app/(shell)/training/load/page.tsx`) muestra hoy el **ACWR crudo** como número (ej. `1.24`) sobre una barra con una **zona verde fija 0.8–1.3**. La auditoría competitiva v2 **refutó adversarialmente** (voto 3-0 en contra) esos umbrales fijos de ACWR como heurística con respaldo sólido (ver spec v2 §4). Además, un ratio adimensional es difícil de interpretar para el atleta.

**Objetivo:** sustituir en la UI ese indicador por una **banda de rango personalizada** al estilo Strava, con semáforo, que se lee de un vistazo y que se define con **los propios datos del atleta**, no con constantes de la industria.

## 2. Decisión de alcance

**Reemplazar en UI, conservar en motor.** La banda pasa a ser el indicador principal de carga en la pantalla. El ACWR (`LoadMetrics.acwr`) **se sigue calculando** en `lib/load.ts` — el coach IA y el backend pueden referenciarlo — pero **desaparece de la interfaz**, junto con su copy de umbrales fijos 0.8–1.3.

> ⚠️ Decisión tomada con criterio mientras el usuario estaba ausente. Revisable: alternativas eran "reemplazar del todo" (quitar también el cálculo) o "complementar" (mantener el número ACWR visible como dato avanzado).

Se mantienen sin cambios las tarjetas de **Carga semanal** (barras 7 días), **Monotonía** y **Tensión**, y la de **Estado de hoy** (recuperación).

## 3. Concepto: la banda como rango propio

En vez de comparar contra umbrales externos, la banda describe **"¿esta semana está dentro de tu rango habitual?"**:

- 🔵 **Descarga** — por debajo de tu rango: semana suave / deload.
- 🟢 **Sostenible** — dentro de tu rango habitual de las últimas ~3 semanas.
- 🟠 **Elevada** — por encima de tu rango: vigila la recuperación.
- 🔴 **Alta** — muy por encima de tu rango: prioriza recuperación.

El "rango" no es un número inventado: es la **distribución de tu propia carga semanal reciente**.

## 4. Algoritmo (cliente, `lib/load.ts`)

Se añade una función `loadBand(daily28, weekAU, historyDays)` y un campo `band: LoadBand | null` a `LoadMetrics`. Reutiliza el `daily28` que `loadMetrics` ya computa (sin recolectar de nuevo).

**Baseline (rango personal):** sobre `daily28` (índice 27 = hoy), se toman las **ventanas móviles de 7 días de las semanas anteriores a la semana en curso** (días 21–27), para no dejar que la carga de esta semana defina su propia banda:

- Sea `d0 = 28 − historyDays` el primer índice con datos reales. Las ventanas válidas son las de 7 días **completas y dentro del historial** que terminan antes de la semana actual: día-fin `e ∈ [max(6, d0 + 6), 20]`, con `sample_e = Σ daily28[e−6 .. e]`.
- Nº de muestras = `20 − max(6, d0+6) + 1`: crece con el historial → 1 muestra a los 14 días (d0=14), 8 a los 21 días, **15 a los 28 días** (d0=0, ventanas 6–20 = 3 semanas completas). Así ninguna ventana incluye días previos al primer entreno (evita hundir `μ` con ceros ficticios).
- `μ` = media de las muestras, `σ` = desviación típica (con 1 muestra, `σ = 0` → lo absorbe el suelo `σ_eff`).
- **Suelo de anchura:** `σ_eff = max(σ, 0.10·μ)` — evita que la banda colapse a una línea cuando el atleta entrena idéntico cada semana. Es un mínimo de anchura **para estabilidad visual**, no un umbral de seguridad.

**Límites de la banda (todo derivado de los datos del atleta):**

| Zona | Rango de carga semanal | Color |
|------|------------------------|-------|
| Descarga (azul) | `weekAU < μ − σ_eff` | azul |
| Sostenible (verde) | `μ − σ_eff ≤ weekAU ≤ μ + σ_eff` | verde |
| Elevada (ámbar) | `μ + σ_eff < weekAU ≤ μ + 2σ_eff` | ámbar |
| Alta (rojo) | `weekAU > μ + 2σ_eff` | rojo |

**Marcador:** la carga de la semana en curso (`weekAU`).

**Gating por historial (reutiliza la lógica `provisional` existente):**

- `historyDays < 14` → `band = null`. Aún no hay una semana completa de baseline antes de la semana actual; la UI muestra estado "calibrando" (como el ACWR provisional hoy).
- `14 ≤ historyDays < 28` → banda visible pero `provisional = true` (rango aún calibrándose).
- `historyDays ≥ 28` → banda plena.

**Casos límite:**

- `weekAU === 0` (sin sesiones esta semana): no se fuerza a "descarga"; la UI muestra "sin sesiones esta semana" (mismo trato que la carga semanal hoy).
- `μ === 0` (sin baseline con carga): `band = null` → estado calibrando.

## 5. Tipo

```ts
export type LoadBandStatus = "descarga" | "sostenible" | "elevada" | "alta";

export type LoadBand = {
  weekAU: number;        // marcador (semana en curso)
  low: number;           // μ − σ_eff  (límite inferior verde)
  high: number;          // μ + σ_eff  (límite superior verde)
  overreach: number;     // μ + 2σ_eff (umbral rojo)
  status: LoadBandStatus;
  provisional: boolean;  // 14..27 días de historial
};
// LoadMetrics gana:  band: LoadBand | null;
```

## 6. UI (`training/load/page.tsx`)

Se sustituye la sección `{/* ACWR */}` (líneas ~98–136) por una tarjeta **"Carga vs tu rango"**:

- **Etiqueta de estado** grande con color del semáforo y texto (`Sostenible`, `Elevada`, …), con punto de color a juego (mismo patrón visual que "Estado de hoy").
- **Banda horizontal** con las cuatro zonas (azul | verde | ámbar | rojo) escaladas, y un marcador (glow neón, reutilizando el estilo del pin de ACWR actual) en la posición de `weekAU`. Escala del eje: de `0` a `μ + 3σ_eff` aprox., para que el marcador nunca se salga.
- **Copy de ayuda (Info)** reescrito: explica que el rango sale de *tus* últimas 3 semanas, no de umbrales médicos. Se elimina el texto de "0.8 y 1.3 = zona segura".
- Aviso `provisional` cuando aplique ("Rango calibrándose: N/28 días").
- Estado calibrando (`band === null`) con el mismo tono que el placeholder de ACWR actual ("Se activa con ~2 semanas de sesiones…").

El icono, el patrón `Info`/`Tip` y el layout `glass` se mantienen. La clave `acwr` del diccionario `INFO` se sustituye por `banda`.

## 7. Backend (parity, follow-up)

El motor de carga de servidor (Django, PR #21) calcula hoy las mismas métricas Foster que `load.ts`. La banda se implementa **primero en cliente** (donde vive la UI). La paridad en servidor —exponer `band` en `fetchServerMetrics`— queda como **follow-up no bloqueante**, igual que se hizo con el motor base: la vista pinta con lo local y, si el servidor lo trae, manda. Hasta entonces `fetchServerMetrics` seguirá sin `band` y la UI usará la banda local.

## 8. Tests (`lib/load.test.ts`)

Nuevos casos para `loadMetrics().band`:

1. `historyDays < 14` → `band === null`.
2. Baseline estable (~3 semanas de carga constante) + semana en curso igual → `status === "sostenible"`.
3. Baseline estable + pico fuerte esta semana → `status === "alta"`.
4. Baseline estable + semana muy suave → `status === "descarga"`.
5. `σ = 0` (todo idéntico) → el suelo `σ_eff` evita banda de anchura cero; una desviación moderada cae en "elevada"/"descarga", no en el límite exacto.
6. `28 días` de historial → `provisional === false`.

Se ejecutan con `pnpm test` (Vitest, ya configurado).

## 9. Fuera de alcance

- No se toca el cálculo de ACWR, monotonía ni tensión (solo se ocultan/mantienen).
- No se implementa la paridad de backend en esta iteración (§7).
- P0.2 (logging fricción mínima) y P0.3 (memoria del coach) son specs aparte.
